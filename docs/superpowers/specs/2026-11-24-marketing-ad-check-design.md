# 마케팅 광고문구검사 화면 설계

## 의도

직원용 목업의 마케팅 담당자 흐름을 현재 React + TypeScript 앱에 추가한다. 사용자는 사이드바의 `광고 문구 검사` 메뉴에서 광고 정보를 입력하고, 검사 결과·진행 상황·검토 보고서 화면으로 이동할 수 있어야 한다.

## 목표

- 기존 `AppShell`, `Sidebar`, `PageHeader`, `Card`, `Button`, `StateView`와 기존 라우팅 방식을 재사용한다.
- `/checks/new` 입력 화면, `/checks/:checkId` 결과 화면, `/progress/:checkId` 진행 상황 화면을 연결한다.
- 대시보드의 `새 광고 문구 검사` 행동과 사이드바 메뉴를 검사 화면으로 연결한다.
- 검사 결과의 `검토 요청 보내기`와 진행 상황의 `검토함 보기`를 기존 `/reviews`·`/reviews/:reviewId` 보고서 흐름으로 연결한다.
- 기존 검토 상세에 목업의 문장별 AI 판정, 근거 경로, `맞음/다름` 피드백 영역을 추가한다.
- API 계약이 확인되지 않은 상태에서는 실제 서버 요청을 추측하지 않고 `not-configured` 상태를 표시한다.
- 기존 fixture 선택 방식으로 목업의 입력·결과·진행 흐름을 시각적으로 검증할 수 있게 한다.
- 반복 UI를 컴포넌트로 분리하고 모바일에서도 입력·결과·진행 단계가 읽히게 한다.

## 비목표

- 확인되지 않은 광고 검사 API 엔드포인트, 요청 필드, 인증·권한 모델을 추측하지 않는다.
- 목업의 제품명, 광고 문구, 수치, 날짜를 운영 데이터로 하드코딩하지 않는다.
- 실제 AI 판정·법률 판단·그래프 검색을 프론트에서 재구현하지 않는다.
- 기존 법무 담당자용 `/reviews` 흐름을 마케팅 검사 흐름으로 대체하지 않는다.

## 접근 방식과 선택

1. 메뉴만 추가하고 안내 상태만 제공한다. 위험은 낮지만 목업의 핵심 작업을 수행할 수 없다.
2. 마케팅 검사 흐름을 별도 라우트와 타입 경계로 추가한다. 기존 공통 UI와 Provider 구조를 유지하면서 현재 API 미확인 제약을 지킬 수 있으므로 선택한다.
3. `/reviews`를 재사용한다. 구현량은 적지만 역할과 업무 단계가 섞여 이후 API 연결과 권한 처리에 불리하므로 채택하지 않는다.

## 라우트와 연결

| 화면 | 라우트 | 연결 |
| --- | --- | --- |
| 광고 문구 검사 | `/checks/new` | 사이드바, 대시보드의 새 검사 버튼 |
| 검사 결과 | `/checks/:checkId` | 자동 검사 시작 후 이동, 다시 검사하기와 진행 상황 이동 |
| 진행 상황 | `/progress/:checkId` | 사이드바와 결과 화면의 진행 상황 보기 |
| 검토 보고서 목록 | `/reviews` | 결과에서 요청된 보고서와 담당자별 배정 보고서 확인 |
| 검토 보고서 상세 | `/reviews/:reviewId` | 문장별 판정·근거·의견·승인/수정 요청 처리 |

입력 화면은 광고명, 제품 유형, 주요 원료, 게시 채널, 광고 문구를 입력받는다. `임시 저장`과 `자동 검사 시작`은 API 계약이 없을 때 설정 안내 상태를 보여 주며, fixture 모드에서는 결과 라우트로 이동한다. 결과 화면에서는 위반 의심·애매·안전 문장과 허가 문구·근거·유사 적발 사례·대안 문구를 구분해 보여 준다.

## 데이터와 API 경계

`CheckDataProvider`를 추가하고 페이지는 인터페이스만 사용한다. `ApiCheckProvider`는 `VITE_API_BASE_URL`과 확인된 계약이 없으면 `not-configured`를 반환한다. `FixtureCheckProvider`는 기존 `VITE_USE_FIXTURES`와 `scenario` 선택 규칙을 따르며, 화면 검증용 데이터만 제공한다. `any`는 사용하지 않고 API 응답은 `unknown`에서 타입 가드로 좁힌다.

## 컴포넌트 구성

- `CheckFormPage`: 입력 상태, 유효성, 저장·검사 시작 동작
- `CheckResultPage`: 판정 요약, 문장별 finding, 근거·대안, 다음 단계
- `ProgressPage`: 단계 목록과 현재 단계
- `AdCheckForm`, `FindingList`, `EvidenceCard`, `CheckProgressStepper`
- `ReviewEvidencePanel`, `ReviewFeedbackControls`를 기존 검토 상세에 추가
- 기존 `Sidebar`, `DashboardPage`에 메뉴와 링크 추가

## 상태·접근성·반응형

- 입력: 필수값 누락, 제출 중, API 미설정, 저장 실패 상태를 표시한다.
- 결과: 로딩, 빈 결과, API 미설정, 오류, 읽기 전용 상태를 표시한다.
- 모든 입력은 label과 연결하고, 오류는 `role="alert"`, 진행 상태는 `role="status"`를 사용한다.
- 데스크톱에서는 목업처럼 입력/안내와 결과/진행을 2열로 배치하고, 모바일에서는 1열로 쌓는다.

## 목업 범위 재점검 결과

- 현재 Artifact 41개 상태는 법무 담당자용 대시보드·검토함·검토 상세·알림·계정 흐름으로 확인했다.
- 별도 직원용 목업 8개 중 이번 요청과 직접 연결되는 화면은 홈의 검사 진입, 광고 문구 검사, 검사 결과, 진행 상황, 검토함, 검토 상세다.
- 관리자 전용 `매뉴얼 추출`과 `업무 흐름 관리`는 API·권한·파일 업로드 계약이 확인되지 않아 이번 변경에서 동작 화면으로 추가하지 않는다. 누락으로 숨기지 않고 별도 후속 범위로 남긴다.

## 검증

- 라우팅·메뉴·입력 검증·fixture 결과 이동에 대한 Vitest + Testing Library 테스트를 먼저 작성한다.
- `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`를 실행한다.
- fixture 모드에서 `/checks/new` → `/checks/:checkId` → `/progress/:checkId` → `/reviews` → `/reviews/:reviewId` 흐름과 모바일 레이아웃을 브라우저에서 확인한다.
- API 미설정 기본 모드에서 확인 안내가 표시되는지 확인한다.
