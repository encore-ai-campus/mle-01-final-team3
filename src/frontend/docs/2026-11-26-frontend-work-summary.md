# 프런트엔드 작업 통합 요약

> 작성 목적: Git stash에 보관되어 있던 프런트엔드 설계·구현 계획 문서의 핵심 결정과 검증 기준을 한 문서로 통합한다.

## 1. 프로젝트와 범위

- 주제: 식품 광고 심의 후속조치 및 게시 검증 AI 에이전트
- 프런트엔드 기술: React, TypeScript, Vite, React Router, Vitest, Testing Library, plain CSS
- 제품 코드 기준 경로: `src/frontend`
- 목업은 41개 아트보드와 5개 페이지 템플릿으로 해석한다. 아트보드 수만큼 라우트를 만들지 않고, 상태·필터·모달·권한 변형으로 테스트한다.
- 실제 API 계약이 확인되기 전에는 엔드포인트·요청 필드·응답 필드·권한 동작을 추측하지 않는다.

## 2. 기본 구조와 데이터 연결

페이지는 `DataProvider`와 `CheckDataProvider` 인터페이스만 사용한다.

- `ApiProvider`: 확인된 API 계약과 `VITE_API_BASE_URL`이 없으면 `not-configured` 상태를 반환한다.
- `FixtureProvider`, `FixtureCheckProvider`: API가 준비되지 않은 시연·테스트 환경에서만 사용하는 가상 데이터 공급자다.
- API 응답은 `unknown`으로 받은 뒤 타입 가드로 좁히며 `any`를 사용하지 않는다.
- 로딩·빈 데이터·오류·권한 거부·API 미설정 상태를 화면에서 구분한다.
- mutation은 성공 응답을 확인한 뒤에만 화면 상태를 갱신하고, 실패 시 입력을 보존하며 중복 제출을 막는다.
- 광고 검사와 검토함은 공유 fixture workflow store를 사용해 같은 문서의 상태 변경이 양쪽 화면에 반영되도록 한다.

## 3. 주요 라우트와 보고서 확인 흐름

| 기능 | 라우트 | 핵심 동작 |
| --- | --- | --- |
| 대시보드 | `/` | 처리 현황과 최근 보고서 확인 |
| 광고 문구 검사 | `/checks/new` | 광고 정보 입력 후 검사 실행 |
| 검사 결과 | `/checks/:checkId` | 마케팅 보고서, 판정 근거, 추천 문구 확인 |
| 진행 상황 | `/progress/:checkId` | 검사 단계와 현재 상태 확인 |
| 검토함 | `/reviews` | 검색·상태 필터·문서 수정·상세 보기 |
| 문서 상세 | `/reviews/:reviewId` | 현재 상태에 맞는 보고서와 처리 액션 확인 |
| 보고서 상세 | `/reviews/:reviewId/reports/:reportStage` | `marketing` 또는 `legal` 보고서 직접 확인 |
| 계정 | `/account` | 로그인 사용자 정보와 비밀번호 변경 |
| 알림 | `/notifications` | 기존 알림 상태 확인용 라우트 |

보고서는 다음 두 종류로 통합한다.

- `[마케팅]광고 문구 검토 보고서`
- `[법무]광고 문구 검토 보고서`

검토함 상세에서 상태에 따라 보고서 탭과 참조 링크를 표시하고, 법무 보고서에서는 같은 문서의 마케팅 보고서로 이동할 수 있게 한다.

## 4. 광고 문구 검사 업무 흐름

### 적합

1. 광고 문구 검사 결과를 마케팅 보고서에 표시한다.
2. 문서 상태를 `[마케팅]검토 완료(적합)`으로 저장한다.
3. `법무팀 검토 요청`과 `닫기`를 표시한다.
4. 법무팀 검토 요청 시 `[법무]검토 대기`로 변경하고 검토함으로 이동한다.
5. 닫기 시 현재 상태를 저장하고 검토함으로 이동한다.

### 부적합

1. 문서 상태를 `[마케팅]검토 완료(부적합)`으로 저장한다.
2. 추천 광고 문구와 `심의 취소`, `AI 추천 요청`을 표시한다.
3. 심의 취소 시 `[마케팅]심의 취소`로 저장하고 검토함으로 이동한다.
4. AI 추천 요청 시 추천 문구 팝업을 표시한다.
5. 팝업에서 광고 문구 검사 요청을 하면 새 검사 결과로 이동하고, 닫으면 검토함으로 이동한다.

## 5. 법무 검토 업무 흐름과 권한

문서 상태는 다음 값을 사용한다.

- `[마케팅]검토 완료(적합)`
- `[마케팅]검토 완료(부적합)`
- `[법무]검토 대기`
- `[법무]검토 중`
- `[법무]검토 완료(적합)`
- `[법무]검토 완료(부적합)`
- `[법무]검토 완료(보완 필요)`
- `[법무]검토 완료(진행 가능)`
- `[마케팅]심의 취소`

법무 담당자가 `[법무]검토 대기` 문서를 열면 `[법무]검토 중`으로 전환한다. 법무 검토 화면에는 필수 `의견` 입력창과 다음 버튼을 표시한다.

- `적합`: `[법무]검토 완료(적합)`
- `부적합`: `[법무]검토 완료(부적합)`
- `보완 필요`: `[법무]검토 완료(보완 필요)`
- `진행 가능`: `[법무]검토 완료(진행 가능)`
- `닫기`: 법무 담당자라면 `[법무]검토 중`으로 저장하고 검토함으로 이동

법무 완료 액션은 `team=legal` 컨텍스트 또는 실제 인증 API의 법무 역할에서만 허용한다. 의견이 비어 있으면 저장하지 않는다. 법무 담당자가 아닌 사용자는 보고서를 읽기만 할 수 있다.

## 6. 로그인·업무 배지·관리자 화면

- 베타 로그인 화면에서 이메일과 비밀번호는 입력하지 않아도 로그인할 수 있다.
- 마케팅 담당자 또는 법무 담당자를 선택해 `sessionStorage`에 부서를 저장한다.
- 상단에는 빨간 종 아이콘과 처리 대상 건수를 표시한다.
- 마케팅 배지는 마케팅팀의 미완료 업무를, 법무 배지는 `[법무]검토 대기`와 `[법무]검토 중` 문서를 센다.
- 완료·취소 문서는 제외하며, 100건 이상은 `99+`, 0건은 배지를 숨긴다.
- 아이콘에는 현재 건수를 포함한 `aria-label`을 제공하고 모바일에서도 아이콘과 숫자가 겹치지 않게 한다.
- `VITE_ROLE_GATING=true`일 때만 역할별 메뉴 제한을 복원한다. 기본 시연 모드는 전체 접근이다.
- 관리자 직원 메뉴는 직원목록(`/employees`)과 직원등록(`/employees/new`)으로 나눈다.
- 직원 등록·수정에는 비밀번호 입력을 제공하되 직원 응답 데이터에는 기존 비밀번호를 저장·표시하지 않는다.
- 직원 상세의 삭제 버튼은 관리자 컨텍스트에서만 노출한다.

## 7. 직원관리 기능

- 직원목록: 이름, 소속부서, 메일주소, 연락처, `Active`/`Inactive` 상태 표시와 검색 제공
- 직원 이름 클릭: `/employees/:employeeId` 상세 페이지 이동
- 직원등록: 이름, 소속부서, 메일주소, 연락처, 비밀번호 입력
- 직원수정: 직원 정보와 상태 수정, 비밀번호는 비어 있으면 변경하지 않음
- 관리자 메뉴는 기존 `/employees`·`/employees/new` 라우트를 재사용하고 중복 목록 라우트는 만들지 않는다.

## 8. 레이아웃·접근성·반응형

- `AppShell`, `Sidebar`, `PageHeader`, `Card`, `Button`, `Badge`, `DataTable`, `StateView`를 공통 UI로 재사용한다.
- 반복되는 검토·보고서·직원 UI는 도메인 컴포넌트로 분리한다.
- 모바일에서는 사이드바를 드로어로 전환하고 표는 가로 스크롤 또는 카드형으로 제공한다.
- 입력은 label과 연결하고 오류는 `role="alert"`, 진행 상태는 `role="status"`로 전달한다.
- 키보드 포커스, Escape로 닫기, 닫힌 뒤 원래 포커스 복귀를 유지한다.
- 색상만으로 상태를 전달하지 않고 텍스트·숫자·접근성 이름을 함께 제공한다.

## 9. 저장소 경로와 Vercel

- 기존 `front/`를 `src/frontend/`로 이동했다.
- Vercel Root Directory는 `src/frontend`, 빌드 출력은 `dist`를 사용한다.
- SPA 직접 진입을 위해 `src/frontend/vercel.json`에서 `/index.html` rewrite를 유지한다.
- `.env`, `.vercel`, `node_modules`, `dist`, API 키·비밀번호는 Git에 포함하지 않는다.
- Vercel Git 연동의 Root Directory 설정은 외부 프로젝트 설정이므로 대시보드 또는 Git 배포 결과로 별도 확인한다.

## 10. 데이터·EDA 참고 요약

stash에 있던 EDA 보고서의 기록상 결과는 다음과 같다. 아래 수치는 이 통합 문서 작성 시점에 재실행한 값이 아니라 원본 보고서에 기록된 결과다.

- JSON 57개와 JSONL 1개, 총 58개 파일을 분석했다.
- 완전 중복 파일은 0건으로 기록되어 있다.
- I1250과 C002의 공통 조인 키는 1,087,872건이며 1:1 조인이 가능하고, 미일치 175건은 별도 확인 대상이다.
- `DSPSDTLS_SEQ` 중복 1건, 건강기능식품 인정번호 중복 사례가 있어 바로 삭제하지 않고 원본·업체·일자를 비교해야 한다.
- 2022년 온라인 부당광고 사례집은 파일명 확장자 오류로 EDA 대상에서 제외되어 파일명 정정 후 재확인이 필요하다.
- 결측값은 `정보 없음`과 `해당 없음`을 구분해야 하며, 식별자와 분류 코드는 숫자형으로 변환하지 않고 문자열로 유지한다.

## 11. 검증 기준과 남은 확인 사항

기록된 구현 검증 기준은 다음과 같다.

- 전체 Vitest 테스트
- TypeScript 타입 검사
- ESLint
- Vite 프로덕션 빌드
- `git diff --check`
- 데스크톱·모바일 레이아웃과 키보드 접근성
- API 미설정 상태의 안내 화면
- fixture 모드의 광고 검사 → 보고서 → 검토함 → 법무 검토 흐름

현재 실제 API 계약이 확인되지 않은 항목은 다음과 같다.

- API base URL, 인증·인가 방식
- 광고 검사·추천·재검사·법무 검토의 실제 엔드포인트와 상태 조회 방식
- 파일 업로드 확장자·용량·저장 API
- 서버가 관리하는 사용자 역할과 부서 정보
- Vercel 프로젝트의 외부 Root Directory·환경변수 설정

이 항목들은 확인 전까지 fixture 또는 `not-configured` 상태로 유지하고, 확인되지 않은 API를 추측해 구현하지 않는다.
