# AdGuard AI 파인튜닝 구현 가이드

2026년 11월 26일 기준 · 근거 문서 《최종 백엔드 API 설계서.pdf》. 아래 페이지 번호는 PDF 뷰어 기준이다.

**광고 문구와 검색된 근거를 함께 받는 판정 모델 하나를 SFT(지도 파인튜닝)로 학습하고, 최초 심의와 재심의에서 공용으로 사용한다.** 모델은 문장별 판정, 위반 유형 코드, 판단 이유, 사용한 근거 ID를 반환한다. Agent는 이를 검증한 뒤 저장소에서 실제 법령 원문과 출처를 가져와 백엔드 보고서를 완성한다. 첫 실험은 `Qwen/Qwen2.5-7B-Instruct`에 LoRA를 붙여 진행하고, 같은 모델에 같은 검색 근거를 주는 기본 모델과 비교한다. 모델·학습 방식·수치는 이 가이드의 구현 제안이다. API 단계·응답 형식·상태 전이는 첨부 설계서 기준이다.

## 1. 모델이 맡을 범위를 먼저 확정한다

| 단계 | 설계서에서 정한 동작 | 구현 방법과 이유 |
| --- | --- | --- |
| `AI_SCREENING` | 최초 광고 문구를 검색 근거와 함께 판정 | 광고 전체 문맥과 제품 분류를 제공하고, 대상 문장별 적합·부적합을 산출한다. 문장만 주면 앞 문장의 제품명·인정 조건·보충 설명을 놓칠 수 있다. |
| `RA_SUGGEST` | 직전 보고서 및 검토 의견을 바탕으로 추천 문구만 생성 | 별도 프롬프트로 `suggestion: {text, rationale}`을 만든다. 추천은 새 심의 결과가 아니므로 이 단계에서 보고서 버전을 올리지 않는다. |
| `RA_RECHECK` | 마케팅 작성자가 [재심의]를 누르면 추천 문구를 최초 심의와 같은 흐름으로 다시 판정 | 확인한 추천 문구를 새 입력으로 삼아 문장 분리와 근거 검색을 다시 한다. 직전 판정·위반 코드는 새 문구의 정답으로 넘기지 않는다. |
| 법무 의견·게시 | 최신 성공 보고서가 적합일 때만 법무 검토를 요청할 수 있다. 법무는 의견을 전송하고, 마케팅 담당자가 게시 여부를 정한다. | 법무 의견은 추천 단계의 참고 입력으로 사용한다. 모델 출력과 법무 의견, 게시 상태의 저장·권한 처리는 각각 설계된 API로 수행한다. |

근거는 설계서 4~5쪽, 27~34쪽, 부록 C 49~50쪽이다. 판정 성공 시 허용값은 `SUITABLE`과 `UNSUITABLE` 두 가지다. 문장별 `violationCode`는 부적합이면 부록 D 허용 목록의 문자열 하나, 적합이면 `null`이다. `3` 같은 숫자 모양의 코드도 문자열로 보낸다. `제8조 제1항` 같은 상위 조항은 `sources[].reference`에 넣는다. 35쪽의 응답 예시는 형식 설명용이며, 법령 문구와 참고 사례는 공식 출처를 확인해 구축한다. 근거는 설계서 29쪽, 31~35쪽, 52~53쪽이다.

**왜 SFT와 LoRA인가.** SFT는 사람이 확정한 입력-출력 예시로 판정·코드 선택·근거 인용의 일관성을 학습한다. 법령과 고시는 검색 저장소가 관리하므로, 개정 시에는 먼저 근거와 적용 정책을 갱신하고 재평가할 수 있다. 적합·부적합만 분류하는 모델로는 문장마다 어떤 규칙과 사실이 연결되는지 설명할 별도 단계가 필요하다. LoRA는 기본 모델을 고정한 채 작은 어댑터를 학습하므로 기본 모델과 비교하거나 배포 버전을 교체하기 쉽다. 한국어 지원과 Apache 2.0 라이선스가 모델 카드에 명시된 Qwen2.5 7B Instruct를 첫 실험 후보로 삼는다. 한국 식품 광고 판정 성능은 아래 평가셋으로 확인한다. [Qwen 공식 모델 카드](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct) · [Hugging Face PEFT LoRA 문서](https://huggingface.co/docs/peft/package_reference/lora) · [Hugging Face TRL SFT 문서](https://huggingface.co/docs/trl/v0.26.2/en/sft_trainer)

새 시스템의 학습 경로는 자체 또는 승인된 환경의 GPU에서 LoRA를 학습하고, Agent가 내부 모델 서버를 호출하는 방식으로 잡는다. OpenAI 공식 안내 기준, 사용 자격이 있는 기존 조직도 셀프서비스 학습 작업을 2026년 12월 15일부터 새로 생성할 수 없고, 기존 모델의 추론은 기반 모델 종료까지 가능하다. 팀에 이미 쓰는 파인튜닝 모델이 있다면 이 가이드의 평가와 연동부터 적용하고, 서비스 종료일과 교체 가능성을 함께 확인한다. [OpenAI 셀프서비스 파인튜닝 종료 일정](https://developers.openai.com/api/docs/deprecations#update-to-openais-self-serve-fine-tuning)

### 후보 모델 비교와 Qwen2.5 7B 선정 근거

AdGuard의 판정 모델에는 **한국어 문구와 법령 근거를 함께 읽고, 문장별 판정·위반 코드·근거 ID를 짧은 JSON으로 반환하는 능력**이 필요하다. 자체 학습·배포 경로를 기준으로 비슷한 크기의 한국어 특화 모델, Qwen 후속 모델, GPU 예산이 작을 때의 경량 모델을 비교했다.

**공개 한국어 평가에서 확인한 점.** SK텔레콤의 경량 모델 비교표에서 한국어 지시 따르기 지표인 **Ko-IFEval**은 Qwen2.5-7B **60.73**, A.X-4.0-Light **72.99**, Qwen3-8B(사고 모드 끔) **73.39**, EXAONE-3.5-7.8B **65.01**이다. 같은 표의 한국어 지식 지표인 **KMMLU**도 각각 **49.56**, **64.15**, **63.53**, **53.76**이다. 이 수치는 SK텔레콤이 공개한 평가 결과다. A.X와 Qwen3를 우선 비교할 근거가 되며, 식품 광고 위반 탐지·위반 코드 선택·법령 인용은 AdGuard 검증셋에서 별도로 측정한다. [SK텔레콤의 경량 모델 평가표](https://huggingface.co/skt/A.X-4.0-Light#lightweight-model-performance)

**Qwen2.5 7B부터 시작하는 이유.** 이 가이드의 첫 실험은 한국어 판정 예시를 LoRA로 학습한 뒤, 학습 전후의 차이를 기존 Agent 완료 통지까지 확인하는 것이다. Qwen2.5 7B는 비교의 출발점으로 쓸 공개 한국어 점수가 있고, 사고 모드 설정 없이 현재 명세의 텍스트 입력과 짧은 JSON 출력에 맞출 수 있다. BF16 가중치는 약 15.2GB로 Qwen3-8B의 약 16.4GB보다 약 1.2GB 적다. 이 수치는 파라미터 수에 2바이트를 곱한 값이며, 학습과 실제 추론에 필요한 GPU 메모리는 대표 입력과 동시 요청으로 측정한다. A.X는 비슷한 규모와 같은 라이선스에 공개 한국어 성적이 더 높으므로, Qwen2.5 학습에 시간을 더 쓰기 전에 함께 비교한다. [Qwen2.5 모델 규모](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct) · [Qwen3 모델 규모](https://huggingface.co/Qwen/Qwen3-8B) · [SK텔레콤 평가표](https://huggingface.co/skt/A.X-4.0-Light#lightweight-model-performance)

**최종 모델을 고르는 실험 순서**

1. 먼저 Qwen2.5 7B, A.X-4.0-Light, Qwen3-8B를 파인튜닝 없이 같은 검증셋으로 평가한다. 광고 문구, 검색된 근거, 판정 지시, 출력 스키마와 응답 길이 한도를 맞추고, 모델별 채팅 형식·사고 모드·GPU 설정을 기록한다. 메모리가 병목이면 Qwen3 4B를, 세 모델이 경계 사례를 자주 놓치면 Qwen3.5 9B를 추가한다.
2. 정확도와 자원 요건을 충족한 상위 후보는 같은 정답 데이터와 비슷한 학습 예산으로 LoRA를 학습한다. 후보마다 학습 전후의 부적합 재현율, 적합 오탐률, 위반 코드 정확도, 근거의 타당성, 전체 요청 p95 지연과 GPU 메모리를 기록한다. 검증셋에서 선택한 조합은 별도 최종시험으로 확인한다.
3. 8절의 고위험 누락·오탐·지연 기준을 먼저 적용한다. 다른 모델이 그 기준을 충족하면서 위반 탐지나 근거 인용에서 안정적으로 앞서면 해당 모델을 채택한다. 품질 차이가 작으면 같은 부하에서 GPU 사용량과 지연이 낮은 모델을 고른다.

## 2. 근거 검색과 적용할 규칙을 만든다

1. **공식 자료를 조·항·호·목 단위로 저장한다.** 식품표시광고법 제8조, 시행령 제3조·별표 1, 관련 고시, 제품·원료·기능성 인정 자료, 확인 가능한 행정처분 사례를 수집한다. 근거에는 내부 ID, 문서명, 조항, 공식 링크, 원문, 발령번호, 해당 규정의 시행일 및 개정 버전, 연결 가능한 위반 코드와 적용 조건을 둔다. 처분 사례는 참고 자료로 따로 관리한다. 설계서 10쪽의 제품·원료 매칭은 온톨로지와 Agent 쪽에서 처리한다. [식품표시광고법 제8조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029094815) · [시행령 제3조·별표 1](https://www.law.go.kr/LSW/lsInfoP.do?lsId=013453) · [식약처 부당한 표시·광고의 내용 기준](https://www.law.go.kr/LSW/admRulInfoP.do?admRulSeq=2100000269428&chrClsCd=010201)
2. **슈퍼바이저는 주장과 제품 정보를 기준으로 검색 경로를 고른다.** 질병 예방·치료 표현처럼 조항과 유사 표현을 찾는 경우 벡터 검색과 조항·코드 조회를 사용한다. 원료의 기능성 인정, 제품 분류, 허용 문구처럼 연결 관계를 확인해야 하면 GraphRAG를 사용한다. 두 종류가 함께 필요하면 두 검색 결과를 합친 뒤 근거 ID로 중복을 제거한다. 적용 조건과 예외까지 포함해서 검색 상위 후보를 구성한다. 초기에는 문장당 3~5개 후보로 실험하고, 필요한 근거가 빠지는 비율과 입력 길이를 보고 조정한다.
3. **같은 증거 묶음을 학습과 운영에서 사용한다.** 입력에는 광고 분류, 원문과 대상 문장 ID, 필요한 인접 문맥, 확인한 제품·첨부자료 사실, 근거 ID·조항·관련 발췌와 적용 날짜를 담는다. 첨부가 있으면 검토에 필요한 본문을 추출하고 위치를 기록한다. 필수 증빙을 읽을 수 없으면 누락으로 처리한다. 광고·첨부·사례 본문에 명령처럼 보이는 문장이 들어와도 인용 데이터로 다룬다. 모델에 실행 권한이나 저장소 자격 증명을 전달할 필요가 없다.
4. **시행일 정책은 검색 계층에서 명시하고 기록한다.** 설계서 10·33·49쪽은 시행 전 버전도 적용하고 판정일 이후 시행일이면 화면에 표시하도록 정한다. 명세를 재현하는 환경에서는 이 정책을 테스트하고, 적용 버전의 `noticeNo`·`effectiveDate`를 보고서에 담는다. 실제 운영에서 현재 광고의 적법성을 검토하는 목적이라면 광고 시점의 시행 조문, 부칙·경과조치, 제품 적용 요건을 기준으로 삼을지 법무와 확정한다. 미래 기준을 사전 점검하는 경우에도 어떤 기준을 썼는지 별도로 기록한다. 예를 들어 제2026-70호는 2026년 10월 23일 발령, 2028년 1월 1일 시행으로 공식 원문에 표시된다. 정책이 바뀌면 검색·라벨 버전을 갱신하고 같은 문구를 다시 평가한다. [일반식품 기능성 표시·광고 관련 고시 제2026-70호](https://www.law.go.kr/admRulLsInfoP.do?admRulSeq=2100000287310) · [선행 시행 버전](https://www.law.go.kr/admRulLsInfoP.do?admRulSeq=2100000248274)

## 3. 정답 데이터를 만들고 평가셋을 고정한다

| 순서 | 할 일 | 이 단계가 필요한 이유 |
| --- | --- | --- |
| 1 | 원본 광고와 재심의 문구를 프로젝트 내 사용 가능한 자료에서 수집한다. 제품 분류는 `GENERAL_FOOD`, `HEALTH_FUNCTIONAL_FOOD`, `CHILDREN_PREFERRED_FOOD`로 정규화한다. 광고와 첨부에서 개인식별정보·내부 식별정보 등 판단에 불필요한 필드는 제거한다. | 운영 요청과 비슷한 입력이 필요하다. 개인정보나 내부 작성자 정보가 정답의 단서가 되면 새로운 광고로 일반화하기 어렵다. |
| 2 | 광고를 문장·불릿 단위로 나누고 원문 순서대로 `s1`, `s2`를 부여한다. 광고 전체 및 문장 위치를 별도로 보관한다. | 제목과 각주를 합쳐야 드러나는 주장이나 숫자·단위·제품명에 든 마침표를 보존할 수 있다. |
| 3 | 검수자가 문장별 정답, 대표 코드, 근거 ID, 짧은 이유, 판단에 사용한 사실을 확정한다. 애매한 표본은 2명이 검토하고 근거가 충돌하면 책임 검수자가 확정한다. 기존 모델 결과, 법무 의견 전송 여부, 게시 처리 여부는 라벨 후보를 찾을 때만 참고한다. | 과거 모델 오판이나 업무 상태를 정답으로 학습하는 일을 막는다. |
| 4 | 쉬운 적합·부적합과 경계 사례를 모두 모은다. 같은 표현에서 제품 분류·기능성 인정 범위·고시 시행일만 달라져 결론이 달라지는 쌍, 허용 표현 옆에 위반 문장이 있는 광고, 예외 요건 누락과 재심의 사례를 포함한다. | 키워드만으로 판정하는 모델은 같은 표현의 적용 조건을 구별하기 어렵다. |
| 5 | 같은 `reviewId`의 원본·재심의, 동일 캠페인·유사 문구를 한 그룹으로 묶는다. 그룹 단위 70/15/15를 출발점으로 학습·검증·최종시험을 나눈다. 가능하면 더 최근인 미등장 캠페인을 최종시험에 넣는다. 시험 광고의 정답 보고서와 사실상 동일한 사례가 검색 인덱스에서 바로 반환되지 않는지도 점검한다. | 수정 전후 문구나 정답 보고서가 여러 분할에 들어가면 실제보다 성능이 높게 나온다. |
| 6 | 처음에는 검수된 학습 예시 약 50개로 데이터와 학습이 연결되는지 확인한다. 검증·최종시험 표본은 따로 확보한다. 이후 고위험 코드와 제품군별 표본 수를 늘리고 수치를 보고한다. | 50건은 제작 파이프라인을 검증하기 위한 출발점이다. 20건 시험에서 1건은 5%p이므로 이 규모로 배포 성능을 일반화하기 어렵다. |

내부 라벨 원장에 `sampleId`, `groupId`, `stage`, `reviewedAt`, 제품 분류, 대상 문장·전체 문맥, 검수자 승인 여부, 정답과 근거 ID, `policyVersion`, `evidenceSnapshot`을 남긴다. 학습용 JSONL에는 실제 모델 입력과 정답만 내보낸다. 구형 보고서의 부적합 문장에 `violationCode=null`이 있을 수 있으므로 검수자가 채운 후 학습에 쓴다. 한 문장에 여러 코드가 맞으면 근거와 후보를 라벨 원장에 남기고, 합의한 대표 코드 선택 기준으로 API 필드 하나를 정한다. 무근거·출처 충돌 표본은 평가의 실패 처리 테스트에 포함하고, 판정 성공 정답에서 제외한다. [OpenAI SFT 문서의 평가·데이터 규모 설명](https://developers.openai.com/api/docs/guides/supervised-fine-tuning)

## 4. 모델 입력과 정답 형식을 고정한다

초기 구현에서는 **대상 문장 1개를 한 예시로** 만들고 같은 광고의 주변 문맥을 포함한다. 문장별 근거 검증과 코드 점검이 쉽다. 긴 광고는 제한된 병렬도로 처리하고, 일부 문장만 성공했을 때 전체 보고서로 저장하는 동작은 막는다. 문장별 호출이 지연 예산을 넘으면 같은 출력 항목을 유지한 채 문장 묶음 호출을 별도로 평가한다.

| 구분 | 필드 | 처리 |
| --- | --- | --- |
| Agent 입력 | `sentenceId`, `text`, `context`, `productCategory`, `asOfDate`, `productFacts`, `evidence[]` | `evidence`는 해당 요청에서 선택할 수 있는 ID·유형·적용 조건·발췌를 포함한다. 기본 모델과 LoRA에 같은 내용을 제공한다. |
| 모델 출력 | `sentenceId`, `decision`, `violationCode`, `rationale`, `evidenceIds[]`, `caseIds[]` | 정해진 JSON 객체 하나를 반환한다. `rationale`은 어떤 광고 표현에 어떤 근거를 적용했는지 1~2문장으로 적는다. |
| Agent 조립 | `text`, `sources[]`, `referenceCases[]`, `alternativeText` | 원문은 입력에서 복사한다. ID를 근거 저장소의 레코드로 풀어 `lawText`·URL·시행일을 채운다. 대안 예시가 없으면 `null`을 보낸다. |

### JSONL 샘플

각 줄이 JSON 레코드 하나다. 아래 예시는 인용 원문이 아닌 짧은 근거 요약을 사용한 형식 예시다. `train.jsonl`에는 검수된 학습 예시를, `validation.jsonl`에는 독립 검증 예시를 저장한다. 실제 자료에서는 `productFacts`에 들어가는 사실의 출처와 `evidence`의 공식 원문 버전을 원장에서 추적할 수 있어야 한다.

```jsonl

{"prompt":[{"role":"system","content":"대상 문장을 근거에 따라 검토한다. sentenceId, decision, violationCode, rationale, evidenceIds, caseIds를 가진 JSON 하나를 반환한다. decision은 SUITABLE 또는 UNSUITABLE이며, 적합이면 violationCode는 null이다. 근거와 사례는 입력에 있는 ID만 각각 사용한다."},{"role":"user","content":"{\"sentenceId\":\"s1\",\"text\":\"바삭한 식감의 과자입니다.\",\"context\":\"\",\"productCategory\":\"GENERAL_FOOD\",\"asOfDate\":\"2026-11-26\",\"productFacts\":[\"해당 시제품의 식감 표현 확인\"],\"evidence\":[]}"}],"completion":[{"role":"assistant","content":"{\"sentenceId\":\"s1\",\"decision\":\"SUITABLE\",\"violationCode\":null,\"rationale\":\"확인된 식감만 설명하며 질병이나 기능성 효과를 주장하지 않습니다.\",\"evidenceIds\":[],\"caseIds\":[]}"}]}
```

실제 학습 데이터를 만들 때와 운영에서 호출할 때 동일한 프롬프트 템플릿을 사용한다. JSONL 예시처럼 필드의 의미를 시스템 메시지에 설명하고, 문장에 적용 가능한 코드 후보를 `evidence`에 담는다. 운영에서는 서버에 JSON 스키마를 별도 인자로 전달해 응답 형식도 제한한다. 예시의 `evidence=[]`은 식감처럼 적용 근거 조회가 필요 없는 단순 표현이다. 예외·인정 여부에 따라 결론이 달라지는 주장에서는 필요한 증빙을 확보한 뒤 모델을 호출한다. 검색 결과에 오답 후보도 일부 넣어, 근거의 유무뿐 아니라 적합성을 판별하도록 학습한다.

## 5. 소량으로 LoRA를 학습한다

1. **학습 환경을 분리한다.** 예시는 Linux와 NVIDIA CUDA GPU, BF16 지원 환경 기준이다. PyTorch 설치 후 `python -c 'import torch; print(torch.cuda.is_available(), torch.cuda.is_bf16_supported())'`로 GPU를 확인한다. 모델 카드의 약 76억 파라미터는 BF16에서 가중치만 약 15GB다. 활성값과 실행 메모리가 추가되므로 대표 길이 데이터로 짧은 학습을 먼저 돌린다. 메모리가 모자라면 컨텍스트를 근거가 잘리지 않게 다듬거나, GPU를 변경하거나, 4비트 QLoRA를 별도 후보로 실험한다. [PyTorch 설치 안내](https://pytorch.org/get-started/locally/) · [PEFT 양자화 가이드](https://huggingface.co/docs/peft/developer_guides/quantization)
2. **모델 버전을 고정한다.** 모델 저장소의 실제 커밋 해시를 `BASE_REVISION`에 설정한 뒤 아래 명령을 실행한다. 학습·비교·배포는 모두 이 모델 스냅샷과 토크나이저를 쓴다. 먼저 받은 파일을 같은 경로에 덮어쓰며 여러 커밋을 섞지 않는다. [Hugging Face Hub CLI 문서](https://huggingface.co/docs/huggingface_hub/guides/cli)

```bash
python -m pip install 'trl[peft]==0.26.2' 'transformers>=4.56.1,<5'
hf download Qwen/Qwen2.5-7B-Instruct --revision "$BASE_REVISION" --local-dir ./models/qwen25-7b
python -m pip freeze > requirements-train.lock
```

3. **아래 코드를 `train_judge.py`로 저장하고 첫 실험을 시작한다.** `completion_only_loss=True`로 정답 부분의 토큰에 학습 손실을 적용한다. 단일 GPU에서 배치 1과 누적 8로 시작한다. `r=16`, 학습률 `1e-4`, 최대 2 epoch는 첫 비교를 위한 값이다. 길이 한도 3,072 토큰에는 입력과 정답이 함께 들어간다. 초과 표본은 잘라버리기 전에 근거 후보 수·발췌 길이를 줄이거나 문장 단위로 다시 만든다. 검증은 epoch마다 하되, 배포 후보는 검증셋 생성 결과로 정한다. [TRL SFTConfig·채팅 형식 문서](https://huggingface.co/docs/trl/v0.26.2/en/sft_trainer)

```python
import os

import torch
from datasets import load_dataset
from peft import LoraConfig
from transformers import AutoTokenizer
from trl import SFTConfig, SFTTrainer

base_path = "./models/qwen25-7b"
max_length = 3072
smoke_steps = int(os.environ.get("ADGUARD_SMOKE_STEPS", "-1"))
run_name = os.environ.get("ADGUARD_RUN_NAME", "adguard-judge-v1")
if smoke_steps > 0:
    run_name += "-smoke"
tokenizer = AutoTokenizer.from_pretrained(base_path, local_files_only=True)
dataset = load_dataset(
    "json",
    data_files={"train": "train.jsonl", "validation": "validation.jsonl"},
)

for split in ("train", "validation"):
    for line_no, row in enumerate(dataset[split], start=1):
        token_ids = tokenizer.apply_chat_template(
            row["prompt"] + row["completion"],
            tokenize=True,
            return_dict=True,
            truncation=False,
        )["input_ids"]
        if len(token_ids) > max_length:
            raise ValueError(f"{split}:{line_no} has {len(token_ids)} tokens")

trainer = SFTTrainer(
    model=base_path,
    processing_class=tokenizer,
    train_dataset=dataset["train"],
    eval_dataset=dataset["validation"],
    args=SFTConfig(
        output_dir=f"./checkpoints/{run_name}",
        model_init_kwargs={"dtype": torch.bfloat16, "local_files_only": True},
        bf16=True,
        max_length=max_length,
        eos_token="<|im_end|>",
        completion_only_loss=True,
        per_device_train_batch_size=1,
        per_device_eval_batch_size=1,
        gradient_accumulation_steps=8,
        learning_rate=1e-4,
        num_train_epochs=2,
        max_steps=smoke_steps,
        eval_strategy="epoch",
        save_strategy="epoch",
        prediction_loss_only=True,
        logging_steps=1,
        seed=42,
        report_to="none",
    ),
    peft_config=LoraConfig(
        task_type="CAUSAL_LM",
        r=16,
        lora_alpha=32,
        lora_dropout=0.05,
        target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    ),
)

trainer.train()
trainer.save_model(f"./artifacts/{run_name}")
```

4. **먼저 `ADGUARD_SMOKE_STEPS=2 python train_judge.py`를 실행한다.** 학습이 진행되고, 손실이 유한하고, `-smoke` 폴더에 어댑터 파일이 생성되는지 확인한다. 확인 후 `python train_judge.py`로 전체 학습을 진행한다. 후속 실험은 `ADGUARD_RUN_NAME`을 바꿔 결과와 체크포인트를 보존한다. 검증셋에서 각 epoch의 어댑터로 실제 JSON을 생성해 판정과 인용을 비교한다. `save_model()` 경로에는 마지막 어댑터가 저장되므로 앞 epoch가 더 좋으면 그 체크포인트의 어댑터를 배포 대상으로 지정한다.
5. **재현 정보를 남긴다.** 기본 모델 커밋, 토크나이저, LoRA 어댑터 해시, 패키지 버전, 프롬프트와 스키마 버전, 라벨·근거 스냅샷, GPU·학습 설정, 평가 결과를 실행 단위로 보관한다. 학습·서빙은 별도 환경으로 관리하고, 서빙 패키지 버전도 함께 기록한다.

## 6. Agent가 호출할 모델 서버와 출력 검증을 연결한다

서빙 환경의 GPU·CUDA에 맞는 vLLM을 설치한다. 학습과 동일한 기본 모델 스냅샷과 검증셋에서 선택한 어댑터를 준비한다. 아래는 같은 머신에서 확인하는 예시다. `--lora-modules`의 이름을 API 요청의 `model`에 쓴다. 실제 실행에서는 입력과 응답 토큰 합계가 서빙 제한 이내인지 검사한다. [vLLM GPU 설치 안내](https://docs.vllm.ai/en/stable/getting_started/installation/gpu/) · [vLLM LoRA 서빙 문서](https://docs.vllm.ai/en/stable/features/lora/) · [vLLM 구조화 출력 문서](https://docs.vllm.ai/en/stable/features/structured_outputs/)

```bash
vllm serve ./models/qwen25-7b \
  --host 127.0.0.1 --port 8000 --max-model-len 4096 \
  --enable-lora --max-lora-rank 16 \
  --lora-modules adguard-judge-v1=./artifacts/adguard-judge-v1
```

`POST /v1/chat/completions`에 4절 예시의 `prompt`를 `messages`로 보낸다. 다음은 요청 조립 예시다. `allowed_codes`는 부록 D와 일치하는 백엔드 허용 목록을 불러온 값이다. `finish_reason`이 정상 종료이고 `choices[0].message.content`가 JSON 객체로 파싱되는지 확인한 뒤 아래 내용 검사를 수행한다. [vLLM Chat API의 JSON 스키마 예시](https://docs.vllm.ai/en/stable/features/structured_outputs/)

```python
def build_request(messages, allowed_codes):
    id_list = {"type": "array", "items": {"type": "string"}}
    properties = {
        "sentenceId": {"type": "string"},
        "decision": {"enum": ["SUITABLE", "UNSUITABLE"]},
        "violationCode": {"enum": [*allowed_codes, None]},
        "rationale": {"type": "string"},
        "evidenceIds": id_list,
        "caseIds": id_list,
    }
    return {
        "model": "adguard-judge-v1",
        "messages": messages,
        "temperature": 0,
        "max_tokens": 512,
        "response_format": {
            "type": "json_schema",
            "json_schema": {
                "name": "adguard_finding",
                "schema": {
                    "type": "object",
                    "properties": properties,
                    "required": list(properties),
                    "additionalProperties": False,
                },
            },
        },
    }
```

| Agent 검사 | 통과 조건과 실패 처리 |
| --- | --- |
| 응답 상태와 문장 매핑 | 모델 호출이 정상 종료되고, JSON 파싱과 스키마 검증을 통과하며, 출력 ID가 요청 ID와 일치한다. 각 원문 문장에 결과가 정확히 하나씩 있어야 한다. 출력이 잘렸거나 일부가 누락되면 보고서를 만들지 않는다. |
| 위반 코드 | 적합은 `null`, 부적합은 부록 D 허용 코드이고 인용된 법령 근거와 매핑된다. 코드표에 없는 값을 자동으로 가까운 코드로 바꾸지 않는다. |
| 근거·사례 | 반환된 ID가 이번 요청의 후보에 실제로 있고, 근거·사례 유형이 각각 맞으며, 제품 분류·버전·적용 조건과 충돌하지 않는다. 초기 운영에서는 부적합에 적용 가능한 법령 근거를 최소 하나 요구한다. 모델이 쓴 이유가 인용으로 뒷받침되는지는 별도로 표본 검수한다. |
| 보고서 조립 | 한 문장이라도 부적합이면 보고서 전체를 부적합으로 집계한다는 규칙을 MVP에서 사용하고, 구현 전에 팀 기준으로 확정한다. 적합은 모든 대상 문장이 검증되었을 때만 집계한다. `summary`는 검증된 결과에서 만들고, `improvementNote`와 `alternativeText`는 없으면 `null`, `referenceCases`는 없으면 `[]`이다. |

근거 부족·충돌 시 남은 시간 안에서 보완 검색을 한 번 수행한다. 그래도 판정 근거가 부족하거나 결과 검증이 실패하면 `runStatus=FAILED`와 `error`를 보낸다. 근거 부족은 성공 응답의 제3 판정값으로 추가하지 않는다. 새 오류 코드나 사람이 확인할 경로가 필요하면 Agent·백엔드가 먼저 합의한다. 일시적 연결 오류와 동일 입력으로 해결되지 않는 증빙 누락은 `retryable`을 구분한다.

## 7. 기존 백엔드 API로 보고서를 저장한다

1. 백엔드가 `POST /internal/v1/review-jobs`로 `schemaVersion`, `runId`, `reviewId`, `stage`, 광고명·분류·문구·첨부 참조를 보낸다. `RA_SUGGEST`에는 `baseReportRunId`와 `legalOpinion`도 전달한다. `RA_RECHECK`에는 사용자가 확인한 추천 문구와 `baseReportRunId`를 전달한다. Agent는 접수를 `202`로 응답한다.
2. Agent가 단계를 분기하고 완료 시 `POST /internal/v1/review-runs/{runId}/completion`을 호출한다. 판정 단계 성공에는 `report`, 추천 단계 성공에는 `suggestion: {text, rationale}`, 실행 실패에는 `error`를 보낸다. 아래 예시는 계약 매핑을 보여주는 부적합 판정 성공 통지다. `schemaVersion`의 실제 값·타입은 연결하는 구현과 맞춘다. 예시에서 `lawText`는 `null`이며, 공식 원문을 저장소에 구축한 운영 경로에서는 선택한 레코드의 원문을 가져온다.

```json
{
  "schemaVersion": "1",
  "reviewId": "revw_001",
  "runStatus": "SUCCEEDED",
  "report": {
    "decision": "UNSUITABLE",
    "summary": "질병 치료 효과를 표방한 문장 1개를 확인했습니다.",
    "improvementNote": "질병 치료를 주장하는 표현을 삭제하세요.",
    "findings": [
      {
        "sentenceId": "s1",
        "text": "이 과자는 당뇨병을 치료합니다.",
        "decision": "UNSUITABLE",
        "rationale": "일반 과자에 당뇨병 치료 효과가 있다고 명시했습니다.",
        "violationCode": "1-나",
        "sources": [
          {
            "title": "식품 등의 표시·광고에 관한 법률 시행령",
            "reference": "제3조 제1항, 별표 1 제1호 나목",
            "url": "https://www.law.go.kr/LSW/lsInfoP.do?lsId=013453",
            "lawText": null,
            "noticeNo": null,
            "effectiveDate": "2025-09-19"
          }
        ],
        "referenceCases": [],
        "alternativeText": null
      }
    ]
  }
}
```

3. 백엔드는 서비스 인증과 `runId`·`reviewId` 일치를 확인한 뒤 실행 결과와 보고서를 함께 저장하고 `200`을 응답한다. 신규 부적합 판정의 코드가 없거나 허용 목록 밖이면 `422 VALIDATION_ERROR`다. 기존 보고서 조회는 33쪽의 하위 호환 규칙에 따라 과거 `null`을 허용한다. 백엔드가 `version`과 `reviewedText`를 저장하며, 최초 성공은 v1, 재심의 성공마다 1씩 증가한다. 추천 생성·닫기·실패는 새 보고서 버전을 만들지 않는다.
4. **중복·타임아웃을 테스트한다.** 같은 실행 요청과 완료 통지는 한 번만 반영한다. 콜백 전송 실패 시 확정된 결과와 같은 `runId`를 사용해 재전송한다. 이 재전송과 사용자의 [다시 검토]를 구분한다. 사용자의 재시도는 새 `runId`이며 최초 실행별 최대 2회다. 180초에 확정된 `FAILED / RUN_TIMEOUT` 또는 이미 저장된 실행을 늦은 결과가 바꾸지 않게 한다. 화면의 60초 폴링은 조회 세션에 적용된다. Agent의 큐·검색·추론·검증·콜백에 개별 시간 한도를 배정해 백엔드 한도 안에서 종료하도록 한다. 근거는 설계서 28~38쪽이다.

## 8. 같은 조건에서 비교하고 통과한 모델을 배포한다

**세 가지 실험을 같은 검증셋에서 수행한다.** ① 기본 모델과 승인된 정답 근거를 사용해 판정 자체의 오류를 본다. ② 기본 모델과 실제 검색 결과를 사용해 현재 서비스 기준선을 만든다. ③ LoRA 모델과 ②의 동일한 검색 결과를 사용해 파인튜닝의 효과를 측정한다. ②·③은 입력·프롬프트·스키마·토큰 한도·채점 기준을 같게 유지한다. 필요하면 ④ LoRA와 승인된 정답 근거로 남은 오류가 검색 때문인지 확인한다. 검증셋으로 후보를 정한 뒤 최종시험을 열어 채점한다.

| 지표 | 계산·확인 방법 | 개선할 곳 |
| --- | --- | --- |
| 부적합 재현율 | 정답이 부적합인 문장 중 부적합으로 맞힌 비율. 고위험 코드, 제품군, 최초·재심의별로 표본 수와 함께 제시한다. 시스템 실패는 맞힌 판정에서 제외하고 실패율도 함께 낸다. | 관련 근거가 검색됐는데 놓치면 프롬프트·라벨·학습 데이터를 본다. |
| 적합 문장 오탐률 | 정답이 적합인 문장 중 부적합으로 판정한 비율. 단순 사실 문구와 기능성 예외 문구를 나눠 본다. | 적합 예시의 다양성, 제품 정보, 예외 조회를 확인한다. |
| 위반 코드 정확도 | 실제 부적합 문장 전체에서 `UNSUITABLE`과 정답 코드가 모두 맞은 비율. 부적합 탐지에 성공한 사례만의 코드 정확도도 함께 낸다. | 혼동이 잦은 코드 쌍과 대표 코드 라벨 기준을 검수한다. |
| 검색 재현율과 인용 정확성 | 정답 근거가 상위 K개 검색 결과에 나타나는지 측정한다. 인용 ID의 유효성은 자동으로, 해당 조항이 설명을 실제로 뒷받침하는지는 사람이 채점한다. | 검색 누락은 인덱스·라우팅을, 근거와 결론 불일치는 판정 모델을 개선한다. |
| 계약과 운영 | 스키마 통과율, 문장 누락·중복, 잘못된 근거 ID, `FAILED` 비율, 광고 건 단위 p95 처리 시간, 180초 초과 건수를 측정한다. | 검색·추론·검증·큐·콜백 시간을 나눠 병목을 찾는다. |

**배포 기준 초안**은 계약 테스트 100% 통과, 고위험 고정 회귀 테스트의 부적합 누락 0건, 최종시험의 부적합 재현율이 기준선 이상, 주요 제품군 오탐률의 허용 범위 준수, 목표 부하에서 전체 p95 60초 이내와 180초 초과 0건이다. 60초는 화면 조회 흐름을 고려한 운영 목표다. 각 제품군의 표본 수, 실패율·오탐률 허용 범위, 신뢰구간을 평가 전에 합의한다. LoRA로 바꿀 근거도 정한다. 예를 들어 탐지율을 유지하면서 코드 정확도가 향상되는지 본다. 표본이 적으면 고위험 0건을 서비스 전체의 무오류로 해석하기 어렵다.

배포 전에는 기준선으로 사용자 응답을 처리하면서 LoRA 후보도 같은 요청으로 비교하는 검증 운영을 한다. 통과하면 소량 트래픽부터 전환한다. 모델·프롬프트·인덱스·규칙 버전을 함께 기록하고, 문제가 생기면 해당 조합을 이전 검증 버전으로 되돌린다. 이미 확정된 보고서는 설계서대로 기록으로 보관한다. 새 평가에서는 최초·재심의 결과 외에 추천만 했을 때의 버전 불변, 증빙 없는 기능성 주장, 시행 전 고시, 422 응답, 중복 완료, 180초 이후 콜백까지 확인한다.
